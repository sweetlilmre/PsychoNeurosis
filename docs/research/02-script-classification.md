# Classification of every script: substrate / pascal / project

Fact-finding pass over all 55 script files in scope (30 in `tools/`, 2 in `tools/dosbox/`, 23 in `v1.31b/`). Every entry below comes from reading the file, not from its name; where a claim was cheap to check mechanically it was checked (import graph, `py_compile` sweep, read-only smoke runs). No file in either repo was modified and no git command was run.

**Tier counts: substrate 10, pascal 22, project 23.**

Legend for the *Disasm* column: `yes` = the script cannot be used without addresses or a segment/block list obtained from a disassembler; `no` = it derives everything it needs from the file itself.

## 1. Genuine overlaps — the same idea implemented twice

**A. Headless period-compiler driver — three implementations of one job.** `v1.31b/build.py` (TP6/6.01/7), `tools/dosbox/dosbuild.py` (TP7 + a TASM pre-step), `tools/dosbox/vtbuild.py` (TP7, release tree). All three stage sources into a DOSBox mount, write a `BUILD.BAT`, run DOSBox-X headless (`-silent -exit`), redirect compiler output to a file *inside* the mount because DOSBox-X is a GUI app that writes nothing to stdout, read the log back from the host, and install what built. They already collide in practice: all three wipe and share the same `build/`, so only one can run at a time.

*Generalise from `build.py`.* It is the only one that treats the compiler as a variable (`COMPILERS` dict, `--tp7`, `--sw=` for a single extra switch), it carries `tp6_dialect()` — the source down-converter that makes a cross-version build possible at all — and its switch set is sourced from an original `TPC.CFG` with a written record of what was omitted and why. What it lacks and must be taken from `dosbuild.py`: the 8.3 staging layer (rename + rewrite `uses` and `{$I}`), the `uses`-graph dependency ordering, and the TASM pre-step. Neither `dosbuild.py` nor `vtbuild.py` is the better base — `vtbuild.py` is `dosbuild.py` with the renaming removed, and is the thinnest of the three.

**B. LZEXE unpacking.** `tools/unlzexe.py` is the implementation; `v1.31b/refpath.py` is the consumer that documents what unpacking *decided* rather than recovered (`maxalloc` written as `$FFFF`, `minalloc` recomputed from SS:SP so its agreeing is partly circular, relocation table re-encoded so only linear targets compare). Not duplicated code, but the pair is one idea split across repos, and the caveat list belongs with the unpacker, not with one project's path helper. `mzinfo.py` detects `LZ91`/`LZ90` and `probe.py` fingerprints the packer; those three plus `refpath`'s caveats are one substrate component.

**C. Segment-layout recovery.** `tools/segmap.py` derives the segment set from relocation fixups (for a binary nobody has mapped yet); `v1.31b/linkorder.py` *predicts* the same layout from the `uses` graph and checks it against a known map. Complementary halves of one component — discovery and prediction — and together they close the loop: `segmap` gives you the original's order, `linkorder` tells you which source shape could have produced it. Generalise both, `linkorder` as the primary, because its rule (reverse DFS post-order) is the reusable fact and `segmap` is twenty lines of Counter.

**D. Byte-exactness comparators.** `v1.31b/verify.py` (`.TPU` vs segment, zero rule, slide-to-locate) and `tools/asmverify.py` (built EXE vs original binary, anchor-align, 1–2-byte holes tolerated as displacements, results locked in `EXPECTED`). Same question at different fidelities. *Generalise from `verify.py`* for the comparator core — its slide-to-locate needs no format parser and cannot be fooled, and its excuse rule is a single stated predicate rather than a heuristic — but take `asmverify.py`'s **regression lock** (`EXPECTED` + `--learn`) into the generic tier unchanged. That lock is the only ratchet in either repo and `verify.py` has nothing like it. Note also that `asmverify.py`'s hole heuristic is the *behavioural*-fidelity answer to the same problem `omf.py`/`asmcheck.py` solve exactly for byte-exact work: three tiers of "excuse this byte", and the generic tool should take the excuse rule as a pluggable mask.

**E. `probe.py` — confirmed name collision, not duplication.** Psycho's fingerprints appended payloads and packers in a binary (substrate, library); VT's compiles a probe unit across three compilers and diffs codegen (pascal, driver). Nothing shared. In a merged toolkit one of them has to be renamed; the substrate one has the weaker claim to the name (`fingerprint.py`), the compiler one is genuinely a probe.

**F. Pascal typed-constant emitter, three copies.** `emit_pascal_data.py` and `emit_pascal_data2.py` each carry their own `fmt`/`fmt_array` with the same hard-won nested-parenthesis rule (flat lists give `Error 88: "(" expected`), and `emit_gain.py` has a third, `.INC`-emitting variant. One `pascal`-tier emitter, three drivers.

**G. `RTL identification`, two idioms.** `rtlmatch.py`/`rtlfind.py` identify RTL routines by masked byte pattern across binaries; `scan_funcs.py` finds *any* routine by prologue/epilogue shape. Both are "locate Borland-emitted code without a disassembler" and belong in one pascal-tier module; neither subsumes the other.

## 4. What most changes how a generic toolkit is drawn

1. **The excuse rule is the pluggable seam, not the comparator.** Four scripts compare bytes and differ only in what difference they forgive: `verify.py` forgives a zero (a `.TPU` fixup), `asmcheck.py`/`omf.py` forgive exactly what the `.OBJ` says is a relocation, `asmverify.py` forgives an isolated 1–2 byte run, `linkcmp.py`/`progcmp.py` forgive an address in a known DGROUP window. One comparator plus a mask provider covers all four, and it makes the strictness of each measurement explicit rather than baked in.
2. **A whole class of measurement needs no disassembler at all.** `census.py` is the thesis stated outright, and `scan_funcs.py`, `rtlmatch.py`, `segmap.py`, `pairmap.py`, `linkorder.py`, `mapcmp.py`, `fpsurvey.py` all belong to it. That is the cheapest and most portable half of the toolkit, and it should be its own layer — a target with no Ghidra project can still be censused, paired and link-ordered on day one.
3. **Two facts in the tree are worth more than any script and are currently buried in docstrings**: TP6's segment layout rule (reverse DFS post-order over `uses`, declaration order, interface before implementation — derived here, documented nowhere) in `linkorder.py`, and the three-lengths footing rule in `mapcmp.py`. A generic tier should carry these as documented knowledge with a test, not as comments inside a driver.
4. **The `project` tier is the largest (23 of 55) but is mostly *emitters*, and emitters are the wrong thing to generalise.** Nine of the 23 exist to turn binary data into a committed source artefact and are done; four more are one file copied five times. The genuinely irreducible project content is small: `NEUROSIS.DAT`'s region map, per-part DGROUP tables, and the `UNITS`/`SEGS` segment tables. Once the block scripts are collapsed and the emitters recognised as spent, the split is closer to substrate 10 / pascal 22 / project ~10 live drivers.
5. **Only one ratchet exists across 55 scripts** — `asmverify.py`'s `EXPECTED` lock, which fails the run when a match gets *shorter*. Everything else reports. For a toolkit whose whole purpose is monotone progress toward exactness, that mechanism should be in the generic comparator rather than in one project's driver.
