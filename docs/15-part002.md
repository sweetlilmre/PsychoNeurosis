# Part 002 — the house and the solid 3-D part

`NEUROSIS.002`, MOD *StarTrek Samples*. 167 functions.

Reconstruction: [`src/PART2.PAS`](../src/PART2.PAS).

## Main body

Only two scenes, and **no DemoVT calls or music fade in the main body** — the
music simply keeps playing. The fade lives inside scene 2.

```pascal
begin
  VGA_SetMode13h; VirtScr_Alloc;
  Demo_Scene1;  FlushKeys;     { 1008:0724  the house }
  Demo_Scene2;  FlushKeys;     { 108b:2454  solid 3-D objects }
  VirtScr_Free; Halt(0);
end.
```

Segment `108b` is **14 KB**, the largest single piece of demo code anywhere in
Psycho Neurosis, and it is a solid-polygon 3-D engine.

## Scene 1 — the house panorama and the garage door

### It is a 1280×200 Mode-X panorama

The four 64,000-byte reads at `$03BE36` are **four Mode-X planes of one wide
image**, not four screens and not four animation frames.

`Scene1_LoadFrames` calls `VGA_SelectPlane(n)` before each read and copies to
`$A000`; `Anim_ShowFrame(page, offset)` is pure hardware panning:

```
addr := PageBase[page] + (offset shr 2)
CRTC $0C/$0D := addr                    { coarse, 4-pixel steps }
wait retrace
AC $13 := (offset and 3) shl 1          { fine, sub-4-pixel }
```

4 × 64,000 = 256,000 = **1280 × 200**, and the scroll runs 0→960 = 1280 − 320.
De-interleaved it is the full house frontage — stained-glass window, front
door, brick walls, big window, and the **garage door at the right-hand end**:
[`panorama_1280x200.png`](../assets/part002/panorama_1280x200.png).

> Reading the planes as separate 320×200 images produced four near-identical
> houses that differed by 29–48%, which looked like animation frames and is
> completely wrong. The tell was in the loader — a plane select before each
> read. See [09-hand-assembler.md](09-hand-assembler.md) and the tunnel scene
> for the same trap.

### The garage door

The 12,412-byte tail is a bitmap with a 2-byte `(width, height)` header. The
header bytes are **zero in the file**; `Scene1_Init` writes 146 and 85 into
them after loading. 146 × 85 + 2 = 12,412 exactly.
[`garage_door.png`](../assets/part002/garage_door.png) is the closed roller
door.

`Door_RaiseOneRow` (`1008:0086`) does the opening:

```pascal
Move(Bitmap[2 + Width], Bitmap[2], 12264);   { scroll up one row }
FillChar(Bitmap[2 + 12264], Width, 128);     { new bottom row = sky }
```

**Colour 128 is a sky mask.** Fifty stars are seeded before the loop —
`X := Random(146) + 1; Y := Random(85) + 1; Colour := Random(3) + 25` — and
each frame they are written into the bitmap **only where the pixel is already
128**, blitted, then restored. So as the door rises, more of the starfield
shows through the opening. Stars step right one pixel per frame, wrapping at
146.

The whole sequence:

| Step | Frames | What |
|---|---:|---|
| pan across the panorama | 961 | hardware scroll 0→960, music-synced |
| door opens with stars | 85 | one row per frame; 85 = the door height |
| stars + palette brighten | 25 | `Palette_BrightenStep`, +3 per channel per frame |
| clear all four planes, fade | 64 | `Palette_FadeOut`, −5 per channel per frame |

## Scene 2 — solid depth-sorted 3-D

`Demo_Scene2` `108b:2454`. Loads 16,580 bytes from `$07D9B2` and sets six
palette entries — white, three greys, two greens.

### Object format

Four objects live in BSS at `DS:$5A56`, `$65A7`, `$70F8`, `$7C49`, a stride of
`$B51` = **2,897 bytes**. In-memory faces are **23 bytes** (`$17`) each: a vertex
count, a colour byte, and up to ten 16-bit vertex indices. Vertices are three
words. The sorted face list starts at object offset `$533`.

### The models are compiled into the executable

`Scene2_Intro` (`108b:1bbd`) is the object *loader*, and it reads from DGROUP,
not from disk — the same pattern as parts 001 and 003. Coordinates are halved
and converted to Real on load. The on-disk face stream is:

```
count, index1 .. indexN, colour        -- count + 2 words per face
```

with indices stored zero-based and incremented on load.

| Object | Verts | Faces | Face sizes | What it is |
|---|---:|---:|---|---|
| [`obj_enterprise`](../assets/part002/obj_enterprise_top.png) | 75 | 55 | 3, 4, 6, 8 | the **USS Enterprise** |
| [`obj_revolver`](../assets/part002/obj_revolver_long.png) | 68 | 64 | 3, 4 | a **revolver** — barrel, cylinder, grip |
| [`obj_sailboat`](../assets/part002/obj_sailboat_long2.png) | 32 | 21 | 3, 4 | a **sailboat** — hull, mast, sail |
| [`obj_quad`](../assets/part002/obj_quad_top.png) | 4 | 1 | 4 | a single quad (ground plane or shadow) |

Extracted and rendered from **five** axis pairs by `tools/vecobj.py`, because a
model is often unrecognisable from the obvious X/Y view. **The top view is what
identifies the Enterprise** — octagonal saucer, engineering hull and neck, and
two rectangular warp nacelles flanking it. The revolver and the sailboat are
both modelled along **Y**, so they only read once Y is horizontal
(`long` / `long2`); from the front all three are ambiguous.

So the sequence reads: pan along the house, the garage door rolls up onto a
starfield, and a procession of unrelated objects drifts past — Enterprise,
revolver, sailboat — under the banner **"WRONG UNIVERSE"**. That is the joke,
and it is why the objects have nothing to do with one another. The soundtrack
is *StarTrek Samples*.

(All three identified by EzE, one of the authors. See
[docs/09](09-hand-assembler.md) for what I got wrong guessing from one
projection.)

### Painter's algorithm

`Obj_Transform` (`108b:0e03`) computes each face's **average Z** by summing its
vertices' Z and dividing by the vertex count, then repeatedly picks the face
with the smallest average and appends it to the sorted list — a back-to-front
depth sort.

### Triangle-fan fill

`Obj_RenderC` walks the sorted faces, gathers each face's projected vertices,
and calls `Poly_FillFan` (`108b:09b1`), which issues `N − 2` calls to `Tri_Fill`
— a **triangle fan**. So the objects are solid, not wireframe.

### Double buffered in Mode-X

`VGA_FlipPage` (`140c:00f4`) waits for display-enable, sets the CRTC start
address, and waits for retrace; the page index toggles `(page + 1) mod 2`.

### Choreographed to the music

`Scene2_Choreography` (`108b:11c1`) is a straight-line script of about a dozen
loops, 12 to 120 frames each, with their own rotation deltas and position
increments, interleaved with `DemoVT_SyncPattern(1, n)` for n = 2, 3, 4, 6.

The code **waits for the music to reach a given MOD pattern** before moving on.
This is the only place in the demo where the music drives the structure rather
than just playing alongside it.

### The three renderers

All three end with a depth-sorted triangle-fan pass; they differ only in what
they draw first.

| Renderer | Address | Draws first |
|---|---|---|
| `Obj_RenderC` | `108b:0a2d` | nothing — polygons only |
| `Obj_RenderA` | `108b:0b42` | 500 background particles |
| `Obj_RenderB` | `108b:0ca1` | 500 particles, then a 34x43 sprite (`108b:0422`) |

34 x 43 = **1,462**, exactly the last read in the region.

### The 12,800-byte buffer

A **320x40 bitmap strip**, drawn by `FUN_108b_1101` at rows 200-239 into both
pages, using palette entries 100-200 from the loaded palette. 40 x 320 = 12,800.

It reads **"WRONG UNIVERSE"** in green on a red-bordered panel —
[`banner_320x40.png`](../assets/part002/banner_320x40.png). The caption for the
UFO sequence.

## The "WRONG UNIVERSE" banner

The 12,800-byte buffer loaded at the start of scene 2 is the **banner bitmap**:
a 320 × 40 image drawn by `108b:1101` at screen rows **200..239** — the bottom
strip of a 320×240 Mode-X screen, below the 3-D object view. It is plotted to

Its colours are 101..200, exactly the range `108b:1101` loads into the palette

## The 1,550-byte block is the font

Scene 2 reads 1,550 bytes at DAT `$080BB2` into `DS:$5448`. This was written
up here as dead, on the grounds that nothing mentions the destination buffer
apart from the `BlockRead` itself. That was wrong twice over.

It is the **5 x 5 bitmap font** `DrawText` (`108b:0000`) draws the two typed
messages with. Nothing mentions `$5448` because the font is indexed off a
DIFFERENT base:

```
    Font[Ord(Ch) * 25 + R * 5 + C]        base DS:$5122
```

and `$5448 - $5122` is 806, which is `32 * 25 + 6` -- so the effective glyph is
`(Ord(Ch) - 32) * 25 + (R - 1) * 5 + (C - 1)`, a clean 5 x 5 biased by 32. The
same trick as part 001's fonts. 1,550 bytes is 62 glyphs, `$20..$5D`, and the
addressable window ends exactly where object 1 begins at `DS:$5A56`.

Bytes are column-major -- `R` is the horizontal axis and `C` the vertical --
and only ever 0 or `$AB`, because `DrawText` just tests `<> 0`:

```
    ..#.. ####. ##### ####. ##### ##### ##### #...# ##### #####
    ..#.. #...# #.... #...# #.... #.... #.... #...# ..#.. ..#..
    .#.#. #..## #.... #...# ###.. ###.. #..## ##### ..#.. ..#..
    .###. #...# #.... #...# #.... #.... #...# #...# ..#.. ..#..
    #...# ####. ##### ####. ##### #.... ##### #...# ##### ##...
```

The second error was the offset. `$07D9B2 + 12,800` is `$080BB2`, not
`$080CB2`; the earlier extraction took 1,550 bytes from 256 bytes too far in,
which is why it looked like meaningless `0`/`$AB` soup. That mis-extraction is
still on disk as [`dead_1550.bin`](../assets/part002/dead_1550.bin) and should
be ignored -- the real block is
[`font_5x5.bin`](../assets/part002/font_5x5.bin).

Part 003 scene 7 loads the same 1,550 bytes at `$11EEC0`; the two files are
byte-identical, so that part very likely has a text drawer of its own.
